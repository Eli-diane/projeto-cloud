# ADR 001 — Usar K3s para o deploy da aplicação

**Status:** Aceito  
**Data:** 08/08/2026

---

## Contexto - Cenário

A aplicação precisava ser colocada no ar de forma acessível pela internet, com capacidade de se recuperar de falhas sozinha e com possibilidade de crescer (escalar) se o número de usuários aumentasse.

O time também queria uma solução que fosse **rápida de configurar**, **com custo baixo** e que não criasse dependência de um único provedor de nuvem.

---

## Alternativas consideradas:

| Opção | O que é | Prós | Contras |
|-------|---------|------|---------|
| **K3s em VM** | Kubernetes leve rodando em uma única máquina virtual | Custo baixo, sobe rápido, fácil de testar, manifests compatíveis com qualquer Kubernetes | Se a VM cair, tudo cai; capacidade fixa; armazenamento efêmero |
| **MKS (Kubernetes Gerenciado)** | Kubernetes gerenciado pela Magalu Cloud | Alta disponibilidade, não preciso gerenciar a infraestrutura | Custo mais alto, demora mais para subir (5-10 min) |
| **VM com Docker Compose** | Rodar a aplicação com Docker em uma única VM | Muito simples de subir | Sem orquestração, sem auto-recuperação, difícil escalar |

---

## Decisão:

**K3s em uma VM BV2-2-40 (Ubuntu 24.04)** com o **Klipper ServiceLB** para expor a aplicação na porta 80.

**Critério principal:** baixo custo e rapidez para começar. Como os manifestos YAML do Kubernetes são os mesmos em qualquer lugar, se um dia precisarmos de alta disponibilidade, podemos migrar para o Kubernetes gerenciado da Magalu (MKS) sem precisar reescrever nada.

---

## Consequências - Perdas e ganhos:

### Positivas 

- Custo menor (paga-se apenas pela VM, não pelo plano de controle)
- Provisionamento rápido (em menos de 2 minutos)
- Manifests YAML compatíveis com qualquer Kubernetes (sem lock-in)
- O Kubernetes reinicia automaticamente o container se ele cair (liveness probe)
- Pode-se aumentar o número de réplicas facilmente se o tráfego crescer
- Experiência prática com Kubernetes (aprendizado valioso)

### Negativas

- **Ponto único de falha:** tudo roda em uma única VM, se ela cair, o sistema cai
- **Armazenamento efêmero:** os dados salvos dentro da VM somem se ela for recriada
- **Capacidade fixa:** a VM tem 2 vCPUs e 2 GB de RAM, não cresce automaticamente
- **IP público pode mudar:** se a VM for recriada, o IP público muda

---

## O que isso significa na prática?

| Pergunta | Resposta |
|----------|----------|
| O sistema fica no ar? | Sim, com 2 réplicas, se um pod falhar, o outro continua atendendo. |
| Se a VM cair, o que acontece? | O sistema fica fora até a VM ser religada ou recriada. |
| Dá para escalar? | Sim, aumentando o número de réplicas ou migrando para uma VM maior. |
| Dá para mudar para o MKS depois? | Sim, os manifests YAML são os mesmos — só trocar o kubeconfig. |
